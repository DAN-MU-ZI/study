# URL Shortener 면접 대비 임시 메모

> 이 문서는 인터뷰 진행 중 답변과 근거를 연결하기 위한 작업용 메모다.
> 저장소의 현재 구현, 과거 실험 기록, 사용자의 실제 경험을 구분해서 적는다.

## 1. 인터뷰 목표 가설

- 가설: 5분 발표에서 URL 단축기의 기능과 시연을 먼저 보여주고, 가장 중점을 둔 구현 한 가지를 실제 코드와 연결해 설명한다.
- 현재 확신도: 90%
- 발표 평가 기준:
  1. 자신이 구현한 기능
  2. 해당 기능이 실제로 작동하는 모습
  3. 구현하면서 가장 중점을 둔 부분
  4. 그 부분이 코드에서 어떻게 구현됐는지
- 아직 확인할 내용: 발표의 중심으로 삼을 구현 한 가지
- 발표 범위에서 제외할 내용: 전체 성능 개선 연대기를 본문으로 길게 설명하는 것

### 발표 의도 확정안

- 중심 구현: ID 생성 과정
- 보여줄 기능: 긴 URL 입력 -> Snowflake 숫자 ID 생성 -> Base62 단축 코드 생성 -> 저장 -> 원본 URL 리디렉션
- 시연: 실제 단축 URL 생성과 리디렉션, k6 및 Grafana를 통한 동작 상태 확인
- 구현 판단: MongoDB Sequence 방식에서 발생한 ID 발급용 DB 왕복과 확장 한계를 줄이기 위해 애플리케이션 Snowflake를 적용
- 코드 연결: `UrlShortenerService`, `AtomicSnowflakeGenerator`, `Base62Codec`
- 결과: 과거 단일 서버에서 목표 11,000 RPS에 근접한 10,902 RPS 기록, 현재는 ALB와 웹 서버 2대 환경을 시연 기준으로 준비
- 발표 본문 제외: 전체 성능 개선 연대기, Redis 상세, Parse, don't validate, Base62 미세 최적화
- 질의응답 후보: Redis 장애 격리, CAS 동시성, worker ID 할당, Base62 최적화, 과거 성능 개선 과정

### 예상 질문: 책은 `shortURL`을 저장하는데 현재 구현은 왜 저장하지 않았는가

- 현재 구현:
  - MongoDB `url_mappings`에는 `id`, `long_url`, `created_at`만 저장한다.
  - 생성 시 Snowflake ID를 Base62로 변환해 반환한다.
  - 조회 시 단축 코드를 Base62 디코딩해 숫자 ID를 얻고, 그 ID로 MongoDB를 조회한다.
- 답변:
  - 현재 요구사항에는 커스텀 별칭과 단축 코드 알고리즘 변경이 없었다.
  - Snowflake ID와 Base62 코드가 일대일로 변환되므로 `shortURL` 컬럼을 저장하면 동일 정보를 중복 저장하게 된다.
  - 따라서 숫자 ID를 MongoDB PK로 사용하고, 단축 코드는 요청 경계에서 디코딩하는 구조를 선택했다.
- 얻는 점:
  - `shortURL` 컬럼과 유일 인덱스를 추가하지 않아 저장 구조와 조회 경로가 단순하다.
  - 별도의 단축 코드 조회 없이 PK 조회가 가능하다.
- 감수한 제약:
  - Base62가 가역적이므로 코드 열거 가능성이 있다.
  - 커스텀 별칭을 지원할 수 없다.
  - 인코딩 규칙을 변경할 때 기존 URL과의 호환 전략이 필요하다.
- 요구사항이 바뀔 경우:
  - 커스텀 별칭이나 비가역 난수화가 필요하면 `short_code`를 유일 키로 저장하는 매핑 구조를 추가한다.
  - 알고리즘 변경 가능성이 생기면 코드 버전 구분 또는 기존 코드 매핑 보존을 함께 설계한다.
- 잘못된 전제 주의:
  - Snowflake도 시간·worker·sequence로 구성된 규칙적인 ID이므로 Base62 변환만으로 유추 가능성이 사라지지 않는다.
  - 분산 ID를 사용한다는 사실만으로 `shortURL` 저장이 필수는 아니다. 숫자 ID와 단축 코드의 변환이 결정적이고 가역적인지가 핵심이다.
  - Key-Value 저장소 조회를 단순히 `O(1)`이라고 단정하지 않는다. 중요한 점은 `shortURL`을 조회 키로 직접 모델링할 수 있다는 것이다.

### Base62와 Redis의 관계

- Base62:
  - 단축 코드를 숫자 ID로 되돌리기 위한 결정적이고 가역적인 코덱이다.
  - Redis miss 또는 장애 시 `shortCode -> id -> MongoDB` 경로를 가능하게 한다.
- Redis:
  - `shortCode -> longUrl` 결과를 저장해 반복 조회에서 MongoDB 조회를 건너뛰는 파생 캐시다.
  - 없어도 기능의 정확성은 유지돼야 하지만, 읽기 성능과 DB 부하 감소를 위해 사용할 수 있다.
- 결론:
  - Base62를 사용한다고 Redis를 제거해야 하는 것은 아니다.
  - 현재 구조는 요청 경계의 `ShortCodeConverter`가 먼저 Base62 디코딩을 수행한다. 이후 Redis hit면 MongoDB 조회를 생략하고, miss/장애면 디코딩된 ID로 MongoDB를 조회한다.
  - 비가역 해시, 난수 코드, 커스텀 별칭을 사용하면 코드에서 숫자 ID를 복원할 수 없다. 이 경우 Redis가 없어도 동작하려면 MongoDB 등에 `short_code -> long_url 또는 id` 매핑을 영속화해야 한다.
- 코덱 변경:
  - 코덱 인터페이스로 구현 교체는 가능하다.
  - 이미 발급된 URL까지 계속 지원하려면 새 코덱 교체만으로는 부족하다. 구버전 코드 판별, 버전별 디코더 또는 영속 매핑 중 하나가 필요하다.

### 인코딩 전략 변경의 운영 문제

- 구분:
  - 구현 최적화: 같은 숫자 ID가 이전과 동일한 문자열로 변환되면 기존 URL과 호환된다.
  - 매핑 규칙 변경: 문자 집합 순서, 진법, 난수화 방식 등이 바뀌어 같은 문자열이 다른 ID로 해석되면 기존 URL이 깨질 수 있다.
- 현재 사례:
  - `StringBuilder + reverse`를 `char[]` 방식으로 최적화한 변경은 Base62 문자 순서와 결과가 같으므로 호환 가능하다.
  - Base62 문자 순서를 변경하거나 비가역 코드 생성 전략으로 교체하면 기존 코드를 새 디코더로 안전하게 해석할 수 없다.
- 코덱 추상화의 한계:
  - 새 코덱 구현으로 교체하는 구조는 만들 수 있지만, 요청으로 들어온 코드가 어느 버전으로 발급됐는지는 알려주지 않는다.
  - 두 디코더에 차례로 넣는 방식은 동일 문자열이 양쪽에서 모두 유효할 수 있어 잘못된 URL로 연결될 위험이 있다.
- 운영 가능한 전략:
  1. 발급된 코드의 매핑 규칙을 변경하지 않고 영구 계약으로 유지한다.
  2. 새 코드에 버전 prefix 또는 별도 경로/도메인을 사용해 디코더를 명확히 선택한다.
  3. `short_code -> id/long_url` 매핑을 영속화해 인코딩 전략과 조회를 분리한다.
  4. 신규 발급만 새 전략으로 전환하고, 기존 디코더는 기존 URL의 수명 동안 유지한다.
- Redis의 위치:
  - Redis는 만료·축출될 수 있는 캐시이므로 구버전 URL 호환성을 보장하는 마이그레이션 저장소로 사용할 수 없다.
  - 버전 또는 매핑 정보는 MongoDB 같은 영속 저장소에 있어야 한다.

### Redis 장애에 대한 운영 관점 답변

- 현재 구현:
  - Redis 조회에서 `DataAccessException`이 발생하면 MongoDB로 fallback한다.
  - 기능은 계속 동작하지만 모든 읽기 요청이 MongoDB로 이동한다.
- 운영 위험:
  - 조회가 쓰기보다 많은 URL 단축기에서 Redis 전체 장애가 발생하면 MongoDB 부하가 급증한다.
  - DB 커넥션 풀 고갈, 지연 증가, 타임아웃으로 이어지는 연쇄 장애가 발생할 수 있다.
  - 따라서 “Redis가 없어도 MongoDB로 조회하므로 문제없다”는 답변은 운영 관점에서 부족하다.
- 더 나은 운영 정책:
  - Redis Sentinel/Cluster 또는 관리형 Multi-AZ 구성으로 캐시 자체의 가용성을 확보한다.
  - Redis 장애를 회로 차단기로 빠르게 감지하고, MongoDB fallback 요청량을 제한한다.
  - rate limit 또는 load shedding으로 DB가 감당할 수 있는 범위만 통과시킨다.
  - hot key는 애플리케이션 로컬 캐시로 한 번 더 보호할 수 있다.
  - TTL jitter, 요청 병합(single-flight), 사전 캐시 워밍으로 동시 miss와 stampede를 줄인다.
  - MongoDB 지연, 커넥션 풀 대기, Redis 오류율을 함께 모니터링한다.
- 면접 답변:
  - “현재 구현은 Redis 장애 시 MongoDB로 fallback해 기능을 유지합니다. 다만 읽기 트래픽 전체가 DB로 몰릴 수 있어 운영 환경에서는 무제한 fallback을 허용하면 안 됩니다. Redis 고가용성을 구성하고, 회로 차단기와 요청 제한으로 DB가 감당 가능한 범위만 fallback시키는 정책이 필요합니다. 현재 코드는 기능적 fallback까지 구현됐고, 장애 확산 방지는 남은 개선 과제입니다.”

## 2. 현재 구현 기준 사실

- 애플리케이션: Spring Boot, Java 17
- 생성 경로: `POST /api/v1/data/shorten`
  - `SnowflakeGenerator.nextId()`
  - `Base62Codec.encode(id)`
  - MongoDB `UrlMapping` 저장
  - Redis `url:{shortUrl}` 캐시 저장, TTL 3600초
- 조회 경로: `GET /api/v1/{shortUrl}`
  - `ShortCodeConverter`에서 Base62 문자열을 ID로 변환
  - Redis 우선 조회
  - miss 또는 Redis 장애 시 MongoDB 조회
  - 조회 성공 후 Redis 갱신
- ID 생성기:
  - 29bit timestamp + 2bit worker + 11bit sequence
  - 초 단위 시간
  - `AtomicLong` CAS로 상태 갱신
  - worker ID 범위 0~3
- 현재 확인된 주의점:
  - README의 Sequence 기반 설명 일부는 현재 코드보다 오래된 상태다.
  - 다중 인스턴스에서는 인스턴스마다 고유 worker ID를 지정해야 한다.
  - `/health`는 의존성 상태를 확인하지 않고 항상 200을 반환한다.

## 3. 과거 실험 기록 기준 사실

- 개선 흐름:
  - FastAPI 초기 구현
  - Spring Boot 더미 API 비교
  - MongoDB 전환과 Redis 접근 경로 정리
  - Random Salt + Hash에서 Sequence + Base62로 전환
  - DB Sequence 병목 확인
  - 애플리케이션 Snowflake로 ID 발급 이동
  - `synchronized` 구현을 `AtomicLong` CAS로 변경
  - 로컬 부하 발생기와 서버의 CPU 경합을 확인하고 EC2에서 분리 측정
- 최종 기록:
  - 전체 HTTP 처리량 10,902.609 RPS
  - p95 65.43ms
  - 실패율 0%
  - k6 시나리오는 iteration당 POST 1회 + GET 10회
- 해석 제한:
  - 10,902 RPS는 ID 생성기 단독 처리량이 아니다.
  - 초기 설계 문서의 4bit worker 구성과 현재 2bit worker 구현을 섞어서 설명하면 안 된다.
  - 단일 측정 결과와 현재 운영 성능을 동일하게 표현하면 안 된다.

### Q2. 5분 발표 러프 답변

- 발표 시작:
  - 구현 기능은 URL 단축기 서버다.
  - 긴 URL을 Base62로 인코딩된 7자리 코드로 축약한다고 설명했다.
  - 『가상 면접 사례로 배우는 대규모 시스템 설계 기초』의 설계를 바탕으로 대규모 트래픽 처리에 중점을 두었다.
- 시연 계획:
  - k6로 트래픽을 발생시키고 Grafana로 처리 상태를 보여준다.
  - ALB가 요청을 두 웹 서버로 분산하고, private 네트워크의 DB 서버에 저장하는 흐름을 설명한다.
- ID 생성 개선:
  - 기존에는 DB Sequence 값을 받아 Base62로 인코딩했으며, ID 발급과 URL 매핑 저장으로 DB를 두 번 왕복했다.
  - 애플리케이션에서 ID를 생성하기 위해 Snowflake를 선택했다.
  - Spring 멀티스레드 환경의 중복 문제를 테스트로 확인하고 `AtomicLong` CAS로 해결했다고 설명했다.
  - 동일 테스트에서 중복이 사라졌고 RPS가 약 10% 향상됐다고 설명했다.
- 조회 개선:
  - 일반 DB 조회 지연을 줄이기 위해 Redis를 도입했다고 설명했다.
  - Redis 도입 이유와 측정 근거의 전달력이 부족하다고 느끼고 있다.
- 코드 수준 개선:
  - 문자열 검증과 파싱이 분리되어 같은 문자열을 두 번 순회하는 문제를 인식했다.
  - Parse, don't validate를 적용해 Converter에서 파싱하고 하위 계층에는 변환된 값을 전달했다고 설명했다.
  - Base62 디코딩의 `indexOf` 선형 탐색을 배열 매핑으로 바꿔 처리 시간을 약 83% 줄였다고 설명했다.
- 사용자가 느끼는 보완점:
  - 성능 개선 과정 전체가 정확히 기억나지 않는다.
  - Redis 도입 설명의 임팩트와 근거가 부족하다.
- 검증이 필요한 주장:
  - 원본 URL 자체를 Base62로 인코딩하는지
  - 현재 단축 코드가 고정 7자리인지
  - CAS 변경의 목적이 중복 방지였는지, 락 경합 감소였는지
  - 약 10% RPS 향상의 비교 조건
  - Redis 도입 전후의 직접 측정 수치
  - Base62 처리 시간 83% 단축의 벤치마크 조건

### Q2 답변의 저장소 대조 결과

- 바로 수정할 표현:
  - Base62의 입력은 긴 URL이 아니라 Snowflake가 생성한 숫자 ID다.
  - 현재 `Base62Codec.encode()` 결과는 가변 길이다. 7자리는 설계상 최대 42bit 제약을 설명할 때 사용할 수 있지만, 현재 코드가 항상 7자리로 패딩하지는 않는다.
- Snowflake와 CAS:
  - MongoDB Sequence는 ID 발급용 `findAndModify`와 URL 매핑 저장을 각각 수행해 생성 경로에 DB 작업이 두 번 있었다.
  - Snowflake 도입으로 ID 발급을 애플리케이션 내부로 옮겨 ID 발급용 DB 왕복을 제거했다.
  - 최초 Snowflake 구현은 `synchronized nextId()`였고, 이후 `AtomicLong` CAS로 바뀌었다.
  - 동시성 유일성 테스트는 현재 CAS 구현이 16개 스레드에서 1,024개 ID를 중복 없이 생성함을 검증한다.
  - 문서에 기록된 `2,674 -> 2,919 IDs/s`는 약 9.2%의 생성기 단독 테스트 개선이다. 전체 API RPS 개선으로 표현하면 안 된다.
  - CAS의 발표상 핵심은 중복 방지 자체보다 `synchronized`로 보장하던 원자성을 유지하면서 락 경합 가능성을 줄인 것이다.
- Base62 최적화:
  - 과거 인코딩 벤치마크는 `StringBuilder append + reverse`를 `char[]` 역방향 채우기로 변경했다.
  - 기록된 결과는 `163.54 ns/op -> 86.64 ns/op`, 약 1.89배이며 처리 시간 감소율은 약 47%다.
  - `indexOf`를 디코드 테이블로 바꾼 현재 구현은 확인되지만, 이에 대한 83% 벤치마크 근거는 찾지 못했다.
  - 따라서 “배열 매핑으로 83% 단축”은 현재 발표에서 제외하거나 별도 재측정이 필요하다.
- Redis:
  - 조회는 Redis hit면 즉시 반환하고, miss 또는 Redis 장애면 MongoDB를 조회한 후 캐시를 갱신하는 Look-aside 구조다.
  - TTL은 3,600초다.
  - 생성 성공 후 Redis 쓰기가 실패해도 MongoDB 저장 결과는 유지되며, 조회 중 Redis 장애도 MongoDB fallback으로 처리한다.
  - 초기 문서에는 `253.57 -> 547.67 req/s`, 평균 `3.44s -> 1.67s`가 기록되어 있으나, 캐시 외에도 블룸 필터·과도한 로깅 제거와 라이브러리 변경이 함께 포함되어 Redis 단독 효과로 말할 수 없다.
- 전체 성능 개선의 확인 가능한 흐름:
  1. FastAPI 초기 실제 기능: `253.57 req/s`, p95 `8.09s`
  2. 불필요한 로직 제거와 캐시 접근 정리: `547.67 req/s`, p95 `6.33s`
  3. 더미 API 비교 후 Spring Boot 선택
  4. Spring 실제 기능 기준: `897.63 req/s`, p95 `2.17s`
  5. MongoDB 경로 전환: `1,962.70 req/s`, p95 `1.02s`
  6. 가상 스레드 실험: `2,710.84 req/s`, p95 `691.74ms`
  7. WSL/Docker CPU 2코어에서 4코어로 조정: `5,555.85 req/s`, p95 `350.82ms`
  8. Sequence + Base62: `5,982.34 req/s`, p95 `330.83ms`
  9. 검증 부족을 인정하고 Java 17로 되돌린 뒤, DB Sequence 병목을 Snowflake로 개선
  10. 로컬 부하 발생기와 서버의 CPU 경합을 확인하고 EC2로 부하 발생 환경 분리
  11. 최종 혼합 시나리오: 전체 HTTP `10,902.61 req/s`, p95 `65.43ms`, 실패율 0%, dropped iterations 5,126
- 최종 수치의 해석:
  - k6 iteration 하나는 POST 1회와 GET 10회로 구성된다.
  - `10,902.61 req/s`는 ID 생성기 처리량이나 쓰기 RPS가 아니라 생성·조회가 섞인 전체 HTTP 처리량이다.
  - 실제 iteration 처리율은 `991.15/s`이며 목표 1,000 iteration/s에서 5,126건이 drop됐다.
  - 따라서 목표였던 전체 HTTP 약 11,000 RPS를 완전히 달성했다고 표현하면 안 된다.
  - 안전한 표현: “목표 11,000 RPS에 근접한 10,902.61 RPS를 기록했고, 실행된 요청의 실패율은 0%였다. 다만 5,126개의 iteration이 시작되지 못해 목표 부하를 완전히 수용한 결과는 아니다.”
  - 사용자 추가 맥락: 이후 ALB와 웹 서버 2대 구조로 확장했으며, 발표에서는 이 최신 환경을 시연할 예정이다.
  - 발표 적용 원칙: 과거 단일 서버 결과는 “10,902 RPS로 목표에 근접”했다고만 설명한다. ALB 환경의 목표 달성 여부와 dropped iteration 제거 여부는 최신 k6 실행 결과로 판단한다.
- 추가 확인이 필요한 사용자 맥락:
  - ALB 뒤 두 웹 서버와 private DB 서버 구성이 실제 시연 환경에 배포돼 있는지는 저장소 문서만으로 확인되지 않는다.
  - 두 웹 서버가 서로 다른 Snowflake worker ID를 사용하는지 시연 전에 확인해야 한다.
