한국어판의 8장인 「URL 단축기 설계」는 다음 흐름으로 진행된다.

> 요구사항 확정 → 규모 추정 → API와 개략 구조 → 단축 코드 생성 방식 비교 → 상세 처리 흐름 → 확장성 검토

책은 최종적으로 **전역적으로 유일한 숫자 ID를 생성하고, 이를 Base62로 변환해 단축 코드를 만드는 방식**을 선택한다. ([예스24][1])

## 1. 요구사항 확정

URL 단축기는 두 가지 기능을 제공한다.

1. 긴 URL을 입력받아 짧은 URL을 생성한다.
2. 짧은 URL로 요청이 오면 원래 URL로 리디렉션한다.

예시는 다음과 같다.

```text
긴 URL
https://www.systeminterview.com/q=chatsystem&c=loggedin&v=v3&l=long

단축 URL
https://tinyurl.com/y7keocwj
```

책에서 정한 조건은 다음과 같다.

* 하루에 새로운 단축 URL 1억 개 생성
* 단축 코드는 숫자, 영문 소문자, 영문 대문자로 구성
* 단축 URL은 가능한 한 짧게 생성
* 생성된 URL의 삭제와 수정은 고려하지 않음
* 높은 가용성, 확장성, 장애 감내 필요 ([ByteByteGo][2])

여기서 삭제와 수정이 없다는 조건은 설계를 상당히 단순하게 만든다. 기존 URL을 변경하거나 만료시키는 정책, 삭제된 코드의 재사용, 캐시 무효화를 고려하지 않아도 되기 때문이다.

## 2. 개략적인 규모 추정

하루 1억 개의 단축 URL을 생성한다고 가정한다.

```text
초당 쓰기 요청
100,000,000 ÷ 86,400초
≈ 1,160회/초
```

읽기와 쓰기의 비율을 10:1로 가정하면 다음과 같다.

```text
초당 리디렉션 요청
1,160 × 10
≈ 11,600회/초
```

10년 동안 운영하면 저장해야 할 레코드 수는 다음과 같다.

```text
1억 × 365일 × 10년
= 3,650억 개
```

평균 원본 URL 길이를 100바이트로 단순 계산하면 원본 URL만 약 36.5TB가 필요하다. 실제 저장 공간에는 ID, 단축 코드, 인덱스, 행 메타데이터, 복제본 등이 추가되므로 필요한 물리 저장 공간은 더 커진다. ([ByteByteGo][2])

이 계산에서 중요한 점은 1,160 쓰기 RPS 자체보다 **3,650억 개의 키를 충돌 없이 생성하고 장기간 저장해야 한다는 점**이다.

## 3. API 설계

책은 REST 형태로 두 개의 API를 제시한다.

### 단축 URL 생성

```http
POST /api/v1/data/shorten
Content-Type: application/json

{
  "longUrl": "https://example.com/very/long/url"
}
```

응답:

```json
{
  "shortUrl": "https://tinyurl.com/zn9edcu"
}
```

### 원본 URL 리디렉션

```http
GET /zn9edcu
```

서버는 응답 본문에 원본 URL을 전달하는 방식보다 `Location` 헤더를 설정한 리디렉션 응답을 반환한다.

```http
HTTP/1.1 302 Found
Location: https://example.com/very/long/url
```

책의 API 표기는 `GET api/v1/shortUrl`이지만, 실제 서비스에서는 단축 URL 자체가 바로 리디렉션 엔드포인트가 되는 형태가 일반적이다. ([ByteByteGo][2])

## 4. 301과 302 리디렉션

책에서는 301과 302의 선택을 설계상 중요한 판단으로 다룬다.

### 301 Permanent Redirect

브라우저가 리디렉션 결과를 캐시할 수 있다.

```text
첫 번째 요청
사용자 → 단축 서버 → 원본 서버

이후 요청
사용자 → 원본 서버
```

장점은 단축 URL 서버로 들어오는 요청이 감소한다는 점이다. 단점은 이후 요청이 단축 서버를 거치지 않을 수 있으므로 클릭 수와 유입 경로를 정확하게 집계하기 어렵다는 점이다.

### 302 Temporary Redirect

사용자가 단축 URL을 클릭할 때마다 단축 서버를 거친다.

```text
사용자 → 단축 서버 → 원본 서버
```

서버 부하는 증가하지만 클릭 횟수, 요청 시각, 유입 경로와 같은 분석 데이터를 수집하기 쉽다.

따라서 책은 다음 기준을 제시한다.

* 서버 부하 절감이 중요하면 301
* 클릭 분석이 중요하면 302 ([ByteByteGo][2])

## 5. 데이터 모델

처음에는 다음과 같은 메모리 해시 테이블을 생각할 수 있다.

```text
shortURL → longURL
```

하지만 수천억 개의 데이터를 메모리에만 저장하는 것은 비용과 영속성 측면에서 적절하지 않다. 책은 관계형 데이터베이스에 다음 세 컬럼을 저장하는 단순한 모델을 제시한다.

```text
URL_MAPPING
────────────────────────────────────────────
id             BIGINT PRIMARY KEY
short_url      VARCHAR
long_url       VARCHAR
```

예시는 다음과 같다.

```text
id             2009215674938
short_url      zn9edcu
long_url       https://en.wikipedia.org/wiki/Systems_design
```

책의 기본 모델은 `id`, `shortURL`, `longURL` 세 컬럼으로 구성된다. ([ByteByteGo][2])

실제 구현에서는 다음 제약 조건이 필요하다.

```sql
PRIMARY KEY (id)
UNIQUE (short_url)
INDEX (long_url)
```

동일한 원본 URL에 항상 같은 단축 URL을 반환하려면 `long_url`에도 유일 제약을 둘 수 있다. 다만 같은 URL에 대해 여러 단축 링크를 허용하거나 사용자별 링크를 제공한다면 `long_url`을 유일하게 만들 수 없다.

## 6. 단축 코드 길이 계산

사용 가능한 문자는 총 62개다.

```text
숫자       0-9   : 10개
소문자     a-z   : 26개
대문자     A-Z   : 26개
합계              62개
```

길이가 `n`인 단축 코드가 표현할 수 있는 경우의 수는 `62ⁿ`이다.

| 길이 |   표현 가능한 코드 수 |
| -: | ------------: |
|  5 |        약 9억 개 |
|  6 |      약 568억 개 |
|  7 | 약 3조 5,216억 개 |
|  8 |      약 218조 개 |

10년 동안 필요한 값은 3,650억 개다.

```text
62⁶ = 56,800,235,584
62⁷ = 3,521,614,606,208
```

6글자는 부족하고 7글자는 충분하다. 따라서 책의 가정에서는 **7자리 단축 코드**가 최소 길이가 된다. ([ByteByteGo][2])

## 7. 단축 코드 생성 방법 1: 해시와 충돌 해결

첫 번째 방법은 원본 URL을 해싱하는 것이다.

```text
longURL
   ↓
MD5, SHA-1, CRC32 등
   ↓
해시 일부 7자리 사용
   ↓
shortCode
```

MD5나 SHA-1의 결과는 단축 코드로 사용하기에는 너무 길다. 따라서 앞부분 또는 일부 7글자만 사용한다.

```text
SHA-1 결과
0eeae7916c06853901d9ccbefbfcaf4de57ed85b

사용 코드
0eeae79
```

일부만 사용하면 서로 다른 URL에서 같은 코드가 나올 수 있다. 충돌이 발생하면 원본 URL에 미리 정한 문자열을 붙여 다시 해싱한다.

```text
hash(longURL) → abc1234
DB에 abc1234 존재

hash(longURL + salt1) → x8k91ab
DB에 없음

저장
```

처리 흐름은 다음과 같다.

```text
원본 URL 입력
   ↓
해시 계산 후 7자리 추출
   ↓
DB에 코드가 존재하는가?
   ├─ 아니오 → 저장
   └─ 예     → 문자열 추가 후 다시 해싱
```

이 방식은 매번 DB에서 코드 존재 여부를 확인해야 한다. 책에서는 존재 여부 검사의 비용을 줄이는 방법으로 블룸 필터를 언급한다. 블룸 필터에서 코드가 존재하지 않는다고 판단되면 DB를 조회하지 않아도 된다. ([ByteByteGo][2])

특징은 다음과 같다.

* 단축 코드 길이를 고정할 수 있음
* 별도의 분산 ID 생성기가 필요하지 않음
* 코드를 보고 다음 값을 예측하기 어려움
* 충돌 처리가 필요함
* 충돌 검사 때문에 DB 조회가 증가함

## 8. 단축 코드 생성 방법 2: 유일 ID와 Base62

두 번째 방법은 각 URL에 전역적으로 유일한 숫자 ID를 부여하고, 해당 ID를 Base62로 표현하는 것이다.

```text
longURL
   ↓
고유 숫자 ID 생성
   ↓
Base62 인코딩
   ↓
shortCode
```

Base62의 문자 대응은 다음과 같이 정의할 수 있다.

```text
0  ~ 9   → 0 ~ 9
10 ~ 35  → a ~ z
36 ~ 61  → A ~ Z
```

책에서는 숫자 `11157`을 Base62로 변환하는 예를 사용한다.

```text
11157 ÷ 62 = 179 ... 59
179   ÷ 62 = 2   ... 55
2     ÷ 62 = 0   ... 2
```

나머지를 역순으로 읽는다.

```text
2  → '2'
55 → 'T'
59 → 'X'

결과: 2TX
```

따라서 단축 URL은 다음과 같이 생성된다.

```text
https://tinyurl.com/2TX
```

책의 최종 설계는 이 Base62 방식을 선택한다. ([ByteByteGo][2])

여기서 용어를 구분할 필요가 있다.

```text
Base62: 숫자를 짧은 문자열로 표현하는 인코딩
해시: 입력을 고정 길이 값으로 변환하는 함수
```

Base62를 디코딩하면 원본 URL이 나오는 것이 아니라 숫자 ID가 나온다.

```text
zn9edcu
   ↓ Base62 디코딩
2009215674938
   ↓ DB 조회
원본 URL
```

원본 URL 복원은 Base62 자체가 담당하지 않고 데이터베이스의 매핑이 담당한다.

## 9. 두 방식 비교

| 항목       | 해시 후 충돌 해결 | 유일 ID + Base62  |
| -------- | ---------- | --------------- |
| 코드 길이    | 고정 가능      | ID가 커지면서 증가     |
| 충돌       | 발생 가능      | ID가 유일하면 없음     |
| DB 존재 검사 | 필요         | 충돌 검사는 불필요      |
| ID 생성기   | 불필요        | 전역 유일 ID 생성기 필요 |
| 코드 예측    | 비교적 어려움    | 순차 ID라면 예측 가능   |
| 처리 구조    | 충돌 재시도 필요  | 단순한 변환 구조       |

책은 충돌 처리가 없고 처리 흐름이 단순하다는 이유로 Base62 방식을 사용한다. 대신 고도로 분산된 환경에서 전역 유일 ID를 생성해야 하는 문제가 생긴다. ([ByteByteGo][2])

ID 생성 방법으로는 책의 이전 장에서 다룬 분산 ID 생성기를 연결할 수 있다.

```text
Auto Increment DB
Ticket Server
UUID
Snowflake 형태 ID
```

순차 증가 ID를 그대로 Base62로 변환하면 다음 단축 코드를 쉽게 예상할 수 있다는 보안 문제가 있다. 이를 줄이려면 ID 비트 섞기, 암호화된 순열, 난수 오프셋 같은 추가 처리가 필요하다.

## 10. URL 생성 상세 흐름

책이 선택한 생성 절차는 다음과 같다.

```text
1. 클라이언트가 원본 URL을 전송
2. DB에서 해당 원본 URL이 이미 존재하는지 확인
3. 존재하면 기존 단축 URL 반환
4. 존재하지 않으면 새로운 유일 ID 생성
5. ID를 Base62로 변환
6. ID, 단축 코드, 원본 URL을 DB에 저장
7. 단축 URL 반환
```

예를 들면 다음과 같다.

```text
longURL
https://en.wikipedia.org/wiki/Systems_design

ID 생성
2009215674938

Base62 변환
zn9edcu

결과
https://tinyurl.com/zn9edcu
```

DB에는 다음 값이 저장된다.

```text
2009215674938 | zn9edcu | https://en.wikipedia.org/wiki/Systems_design
```

([ByteByteGo][2])

실제 구현에서는 동시에 같은 URL이 들어오는 경우를 처리해야 한다.

```text
요청 A: longURL 없음 확인
요청 B: longURL 없음 확인
요청 A: ID 생성 및 저장
요청 B: 다른 ID 생성 및 저장
```

동일 URL에 동일 코드를 반환해야 한다면 DB 유일 제약, 트랜잭션 또는 멱등성 키가 필요하다.

## 11. 리디렉션 상세 흐름

URL 리디렉션은 읽기 요청이 쓰기보다 많으므로 캐시를 사용한다.

```text
사용자
   ↓
로드 밸런서
   ↓
웹 서버
   ↓
캐시 조회
   ├─ Cache Hit  → 원본 URL 반환
   └─ Cache Miss → DB 조회 → 캐시 저장
                           ↓
                       리디렉션
```

처리 순서는 다음과 같다.

```text
1. 사용자가 단축 URL을 클릭한다.
2. 로드 밸런서가 요청을 웹 서버로 전달한다.
3. 웹 서버가 단축 코드를 캐시에서 조회한다.
4. 캐시에 있으면 원본 URL을 즉시 반환한다.
5. 캐시에 없으면 DB에서 조회한다.
6. 조회 결과를 캐시에 저장한다.
7. Location 헤더와 함께 리디렉션 응답을 반환한다.
```

DB에도 존재하지 않으면 잘못된 단축 코드이므로 일반적으로 `404 Not Found`를 반환한다. 책은 읽기 요청이 더 많다는 가정에 따라 `<shortURL, longURL>` 매핑을 캐시하는 구조를 제시한다. ([ByteByteGo][2])

## 12. 전체 아키텍처

```text
                    ┌──────────────────┐
                    │ 전역 ID 생성기   │
                    └────────┬─────────┘
                             │
사용자 ──▶ 로드 밸런서 ──▶ 웹 서버 ──▶ Base62 변환
                             │
                    ┌────────┴─────────┐
                    │                  │
                    ▼                  ▼
                 캐시              데이터베이스
             short → long       id, short, long
```

생성 요청은 다음 경로를 따른다.

```text
클라이언트
→ 로드 밸런서
→ 웹 서버
→ ID 생성기
→ Base62 변환
→ DB 저장
→ 단축 URL 반환
```

리디렉션 요청은 다음 경로를 따른다.

```text
클라이언트
→ 로드 밸런서
→ 웹 서버
→ 캐시
→ 필요할 경우 DB
→ 301 또는 302 응답
```

## 13. 확장성 검토

책은 면접 시간이 남으면 다음 항목을 추가로 논의하도록 제안한다.

### 웹 서버 확장

웹 서버는 사용자 세션이나 URL 데이터를 로컬에 저장하지 않는 무상태 구조로 만든다. 그러면 로드 밸런서 뒤에 서버를 자유롭게 추가하거나 제거할 수 있다.

### 데이터베이스 확장

데이터가 수천억 건까지 증가하므로 다음 방법을 고려한다.

```text
읽기 복제본
데이터베이스 복제
샤딩
장애 조치
백업
```

샤딩 키로는 `short_url` 또는 숫자 ID를 사용할 수 있다. 해시 기반 샤딩은 데이터가 특정 샤드에 몰리는 현상을 줄일 수 있다.

### 캐시

인기 단축 URL은 반복적으로 조회된다. 캐시는 데이터베이스 읽기 부하와 리디렉션 지연을 줄인다.

일반적인 정책은 다음과 같다.

```text
Cache-Aside

캐시 조회
→ miss
→ DB 조회
→ 캐시에 저장
```

### 처리율 제한

공격자가 대량으로 URL을 생성해 저장 공간이나 ID를 소모할 수 있다. IP, 사용자 계정, API 키를 기준으로 URL 생성 요청의 처리율을 제한한다.

### 분석 시스템

리디렉션 처리와 분석 이벤트 저장을 동기적으로 묶으면 응답이 느려질 수 있다. 실제 구조에서는 리디렉션을 먼저 처리하고 클릭 이벤트를 메시지 큐로 보내 비동기로 집계할 수 있다.

책은 처리율 제한, 무상태 웹 서버 확장, DB 복제와 샤딩, 클릭 분석, 가용성·일관성·안정성을 추가 논점으로 제시한다. ([ByteByteGo][2])

## 최종 정리

책의 설계를 한 문장으로 표현하면 다음과 같다.

```text
분산 ID 생성기가 만든 전역 유일 숫자를 Base62로 인코딩해 단축 코드를 만들고,
매핑은 DB에 영속화하며, 읽기 중심의 리디렉션 요청은 캐시로 처리한다.
```

핵심 설계 판단은 다섯 가지다.

1. 3,650억 개를 수용하기 위해 7자리 Base62 코드를 사용한다.
2. 해시 충돌 방식과 ID 기반 방식을 비교한 뒤 ID 기반 방식을 선택한다.
3. 단축 코드와 원본 URL의 매핑을 데이터베이스에 저장한다.
4. 리디렉션은 읽기 중심이므로 캐시를 둔다.
5. 웹 계층을 무상태로 만들고 DB 복제·샤딩과 처리율 제한을 적용한다.
