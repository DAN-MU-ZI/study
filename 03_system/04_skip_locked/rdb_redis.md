# RDB + Redis 재고 버퍼 부하 테스트

## 목적

동일 상품의 재고 수량 컬럼에 요청이 집중될 때 발생한 RDB 락 경합을 Redis 버퍼로 완화하고, 성능 개선과 함께 새로 생기는 실패 지점을 확인한다.

## 테스트 조건

- 요청: `POST /buy`, 상품 ID 1, 요청당 수량 1개
- 부하: 30초간 VU 10, 60초간 VU 50, 60초간 VU 100, 30초간 감소
- Redis 버퍼 크기: 100개
- 목표: 오류율 1% 미만, p95 500ms 미만, p99 1초 미만
- 비교 대상: 동일 시나리오로 측정한 RDB 단독 구조

## 결과 요약

| 지표 | RDB 단독 | RDB + Redis | 변화 |
| --- | ---: | ---: | ---: |
| 평균 RPS | 17.2 req/s | 415.0 req/s | 약 24.1배 증가 |
| 총 요청 수 | 약 3,000건 | 74,739건 | 약 24.9배 증가 |
| 정상 응답 | 약 3,000건 | 68,222건 | 성공 처리량 약 22배 증가 |
| 평균 응답시간 | 2.62초 | 4.83ms | 약 542배 감소 |
| p95 | 5.45초 | 9.72ms | 약 561배 감소 |
| p99 | 6.35초 | 57.55ms | 약 110배 감소 |
| 오류율 | 0% | 8.71% | 목표 1% 미달 |
| HikariCP pending | 80개 이상 | 0 | 커넥션 대기 해소 |

응답시간 목표는 충족했지만 오류율 목표는 충족하지 못했다. 74,739건 중 6,517건이 실패했으며, 상태 코드 그래프에서 실패 응답은 `409 Conflict`로 확인됐다.

- RDB 단독 구조에서 나타난 커넥션 풀 고갈과 요청 대기 누적은 재현되지 않았다.

![PostgreSQL과 JVM 지표](image-4.png)

- PostgreSQL active 세션은 최대 3개 수준이었다.
- SQL 평균 실행시간은 약 0.2~1.2ms로, RDB 단독 구조의 약 150ms보다 크게 감소했다.
- SQL 호출량은 최대 약 25 ops/s로 제한됐다. 대부분의 구매 요청이 Redis에서 처리되고 버퍼 보충 시점에만 RDB를 사용했기 때문이다.
- deadlock과 HikariCP timeout은 발생하지 않았다.
- JVM CPU, heap, GC pause에서도 포화 징후가 나타나지 않았다.

![JVM 스레드와 Prometheus Target](image-5.png)

- 부하 증가에 따라 live 스레드는 증가했지만 runnable 스레드는 약 10개 수준을 유지했다.
- 애플리케이션, PostgreSQL, Prometheus, Redis exporter의 수집 상태는 정상으로 유지됐다.

## 오류 원인

Redis 버퍼 100개가 소진되면 여러 요청이 동시에 보충을 시도한다. 한 요청만 분산 락을 획득해 RDB에서 버퍼를 가져오며, 락을 얻지 못한 요청은 대기하거나 재시도하지 않고 즉시 `409 Conflict`를 반환한다.

따라서 8.71%의 오류는 재고 부족이나 RDB 처리 한계가 아니라 버퍼 보충 경합을 처리하는 현재 정책에서 발생했다. 오류를 줄이려면 다음 정책을 추가로 결정해야 한다.

- 보충 중인 요청의 제한된 재시도와 backoff
- 재시도 요청의 중복 차감을 막는 멱등성
- RDB 차감 후 Redis 보충 실패에 대한 보상 또는 복구
- Redis 예약 상태와 RDB 원장 상태의 불일치 탐지

## 정합성 검증의 한계

이번 실행은 테스트 시작 직후의 RDB와 Redis 재고를 함께 기록하지 못했다. 따라서 정상 응답 수와 종료 재고를 이용한 정합성 검증은 수행할 수 없다. 다음 비교부터는 아래 조건을 실행 전후에 기록한다.

```text
초기 재고 = 종료 RDB 재고 + 종료 Redis 재고 + 성공 구매 수
```

또한 Redis 연산과 RDB 트랜잭션은 하나의 원자적 작업으로 묶이지 않는다. 성능 결과와 별개로 부분 실패에 대한 복구 정책이 필요하다.

## 결론

Redis 버퍼를 적용하면서 동일 재고 행의 락 경합과 DB 커넥션 대기는 해소됐다. 평균 처리량은 약 24배 증가했고 p95는 5.45초에서 9.72ms로 감소했다.

반면 버퍼 보충 경합에서 8.71%의 `409` 응답이 발생했다. 처리량 개선 이후에는 재시도, 멱등성, 부분 실패 보상과 같은 정책이 새로운 관리 대상이 됐다.

다음 단계에서는 재고를 단위별 행으로 표현하고 `FOR UPDATE SKIP LOCKED`로 잠기지 않은 재고를 선점한다. 예약과 재고 변경을 하나의 RDB 트랜잭션에서 처리한 뒤 같은 부하 조건으로 처리량, 지연시간, 오류율과 재고 정합성을 비교한다.
